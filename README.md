# ns-payments

Сервис приёма платежей: принимает вебхук платёжного провайдера, **перепроверяет платёж через его API**, идемпотентно сохраняет результат, регистрирует фискальный чек и публикует событие для остальных сервисов.

Python 3.12 · FastAPI · SQLAlchemy 2 (async) · PostgreSQL · Alembic · NATS · Docker · pytest · GitHub Actions

---

## Зачем это нужно

Платёжный вебхук — это HTTP-запрос из внешнего мира, который может прийти дважды, с опозданием, в другом порядке или вообще быть подделкой. Если обрабатывать его «как есть», пользователь получит услугу бесплатно или дважды.

Сервис решает три задачи:

1. **Не доверять телу запроса.** Сумма, статус и метаданные берутся из ответа API провайдера, а не из вебхука.
2. **Не зачислить дважды.** Уникальный индекс по `provider_payment_id` + обработка конфликта — повторная доставка превращается в `duplicate`.
3. **Не потерять деньги из-за чека.** Если фискализация недоступна, платёж всё равно сохраняется, а чек помечается `failed` и доедет фоновой проверкой.

## Как это работает

```mermaid
flowchart LR
    U[Пользователь] -->|оплата| P[Платёжный провайдер]
    P -->|webhook| W[FastAPI: /webhooks/yookassa]
    W -->|1. GET /payments/{id}| P
    W -->|2. INSERT payment| DB[(PostgreSQL)]
    W -->|3. чек| F[Фискализация: ЛК НПД]
    W -->|4. событие| NATS[(NATS)]
    NATS --> B[Бот / воркер]
    B -->|выдача услуги| U
```

Порядок обработки:

| Шаг | Что происходит | Если не получилось |
|-----|----------------|---------------------|
| 1 | Валидация тела, отсев не-`payment.succeeded` | `400` / `202` |
| 2 | `GET /payments/{id}` у провайдера | `502` — провайдер повторит доставку |
| 3 | Проверка статуса, валюты, суммы, `user_ref` | `202 ignored` с причиной |
| 4 | `INSERT payments` с уникальным индексом | конфликт → `200 duplicate` |
| 5 | Регистрация чека | ошибка → чек `failed`, платёж сохранён |
| 6 | Публикация события после коммита | событие не уходит по откатившейся транзакции |

## Инженерные решения

**Сверка через API, а не доверие вебхуку.** Тело запроса используется только как «повод»: id платежа. Всё остальное — из `GET /payments/{id}`. Тест `test_payload_amount_is_not_trusted` проверяет, что при сумме 100 ₽ в вебхуке и 50 ₽ у провайдера в базе будет 50 ₽.

**Идемпотентность на уровне БД, а не приложения.** Проверка «а нет ли уже такого платежа» в коде не спасает от гонки двух параллельных вебхуков. Поэтому решает уникальный индекс, а `IntegrityError` внутри `SAVEPOINT` превращается в штатный ответ `duplicate` без поломки внешней транзакции.

**Чек не блокирует деньги.** Внешний вызов внутри транзакции — плохая идея: если ЛК НПД лежит, пользователь останется без услуги. Поэтому ошибка фискализации ловится, пишется в `receipts.error`, а платёж коммитится.

**Событие публикуется после коммита.** Иначе подписчики могут получить `payment.succeeded` по платежу, который откатился. Строгий вариант — transactional outbox; здесь выбран компромисс под нагрузку 80–90 платежей в месяц, ограничение описано ниже.

**Деньги в копейках.** `int` вместо `float`: `Decimal("1499.90") → 149990`, без накопления ошибки округления. Разбор сумм покрыт тестами.

**Зависимости — через протоколы.** `PaymentProvider` и `FiscalProvider` — `Protocol`; в тестах подставляются фейки, в проде — HTTP-клиент YooKassa и клиент ЛК НПД. Сеть в тестах не нужна.

## Быстрый старт

```bash
docker compose up --build
```

Миграции применяются автоматически при старте контейнера. В локальном режиме (`APP_ENV=local`) провайдер подменён фейком, поэтому демо работает без аккаунта YooKassa:

```bash
curl -s -X POST http://localhost:8000/webhooks/yookassa \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "notification",
    "event": "payment.succeeded",
    "object": {"id": "pay_demo_1", "status": "succeeded"}
  }'
# {"status":"processed"}

# Повторная доставка того же вебхука:
# {"status":"duplicate","reason":"already_processed"}

curl -s http://localhost:8000/payments/pay_demo_1
# сумма, статус и чек
```

Без Docker:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
export DATABASE_URL="sqlite+aiosqlite:///./payments.db"
alembic upgrade head
uvicorn app.main:app --reload
```

## Тесты

```bash
pytest -q      # 23 теста, без сети и без БД-сервера (SQLite в памяти)
ruff check .   # линт
```

Что покрыто:

- happy path: платёж сохранён, чек зарегистрирован, событие опубликовано;
- повторный вебхук: одна запись, один чек, одно событие;
- подделка суммы в теле вебхука;
- события не про успешную оплату, неизвестный платёж, отсутствие `user_ref`;
- недоступность провайдера (`502`) и недоступность фискализации (платёж сохранён);
- битый JSON и неполное тело;
- HTTP-клиент YooKassa на `httpx.MockTransport`: успех, `404`, `500`, таймаут;
- разбор сумм: `100.00 → 10000`, отсутствие float-дрейфа.

## Конфигурация

Все настройки — переменные окружения (`app/config.py`, pydantic-settings). Секреты — `SecretStr`, в логи не попадают.

| Переменная | По умолчанию | Комментарий |
|------------|--------------|-------------|
| `DATABASE_URL` | `postgresql+asyncpg://payments:payments@localhost/payments` | строка подключения |
| `APP_ENV` | `local` | `local` → фейковый провайдер |
| `NATS_URL` | — | без NATS события пишутся в лог |
| `EVENTS_SUBJECT` | `payments.succeeded` | subject для события |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | demo | ключи магазина |
| `FISCAL_MODE` | `fake` | `fake` или `nalog` (нужен пакет `nalogovich`) |

## Ограничения и что дальше

Осознанные компромиссы под текущий объём (80–90 платежей в месяц):

- публикация события после коммита не гарантирует доставку при падении между шагами — следующий шаг: transactional outbox;
- нет ретраев публикации и фоновой сверки «оплата есть — события нет»;
- метрик Prometheus в этом репозитории нет: они вынесены в инфраструктуру.

Дальше по плану: outbox + воркер ретраев, метрики и алерты, идемпотентность на уровне HTTP (Idempotency-Key).
